# 3단계 설계: 연결 (모델, MCP, API, 판단 모델)

> 상태: **3a, 3b 구현됨** (OAuth: [mcp-servers.md](mcp-servers.md)의 "Sign in with OAuth") (사용법: [mcp-servers.md](mcp-servers.md)). 3c부터는 아직입니다. 3b에서 바뀐 점: 토큰 교환과 갱신은 워커가 하고, 갱신은 `fn_watchdog`가 만료 5분 전에 큐에 넣습니다. 클라이언트 등록 순서는 사람이 입력한 id, CIMD(https일 때만), DCR입니다. 구현하며 바뀐 점: 새 무상태 방식을 먼저 시도하지 않고 **옛 `initialize` 핸드셰이크를 먼저** 보내며, 서버가 거절하면 무상태 형식(`_meta`와 `Mcp-Method` 헤더)으로 되돌아갑니다(배포된 서버가 대부분 옛 방식이라 더 안전합니다). `mcp_call` 함수는 절차(procedure)에 묶여야만 실행되므로 도구를 등록하면 **같은 이름의 절차도 함께 만들어** 묶고, 에이전트에게는 그 절차를 줍니다. [improvement-plan.md](improvement-plan.md)의 3단계를 현재 코드와 최신 MCP 규격에 맞춰 구체화했습니다. 7장의 결정을 확인한 뒤 3a부터 구현합니다.

## 1. 목표와 범위

PG로 할 수 없는 일을 MCP 서버로 확장하는 길을, **주소 하나 붙여넣고 도구마다 위험 등급을 확인한 뒤 에이전트에게 권한을 주는 것**까지 끝낼 수 있게 합니다. 리서치 MCP(OAuth 포함)를 3분 안에, 장비 제어 MCP의 물리 동작 도구를 기본적으로 "승인 필요"로 등록하는 것이 완료 기준입니다.

원칙은 그대로입니다.

- 모델, MCP 서버, 판단 모델은 모두 PG **밖**에서 돕니다. 로컬(stdio) MCP도 PG 밖에서 HTTP로 중계하고 Allgres는 주소로만 연결합니다.
- 외부 호출은 지금처럼 Rust 워커가 합니다. PG는 연결 정보, 도구 목록, 위험 등급, 승인, 이력을 소유합니다.
- 비밀값(키, 토큰)은 기존 방식(`allgres.secret_key`로 암호화, 목록에 절대 반환하지 않음)을 따릅니다.
- 판단 모델 연결은 선택 사항입니다. 연결이 없어도 모든 판단 지점은 사람과 규칙으로 정상 동작합니다(1단계에서 구현됨).

## 2. 지금 있는 것 (코드에서 확인)

| 영역 | 현재 상태 | 부족한 점 |
|---|---|---|
| 채팅/임베딩 모델 | `llm_providers`(`openai_compat`, `anthropic`, `oauth`), `provider_probes`로 연결 시험, 가격표 | 모델 목록 자동 조회와 가격 자동 입력 없음. 판단 모델용 `purpose` 없음 |
| HTTP API | `api_connections`(`none`, `authorization`, `x-api-key`), 비밀은 `api_connection_secrets` | 연결 시험 없음 |
| MCP | `functions.handler='mcp_call'`이 `api_connections`를 재사용. 워커가 `initialize` → `initialized` → `tools/call` 수행하고 `mcp-session-id`를 전달(`src/outbound.rs`) | **도구 발견 없음**: 도구 이름을 사람이 직접 입력. **인증은 정적 헤더뿐**(OAuth 없음). **위험 등급 없음**. 연결 상태, 도구 목록 변경 감지 없음. 들어오는 이벤트 없음 |
| 승인 | 함수별 정책으로 승인 요구 가능, 1단계에서 결재 라우팅 완성 | 도구가 "읽기"인지 "물리 동작"인지 구분해 기본값을 정하는 곳이 없음 |

핵심 사실: MCP 호출 경로와 SSRF 방어, 승인 경로는 이미 있습니다. 3단계는 **발견, 인증, 등급, 상태**를 얹는 일이고 호출 경로를 새로 만들지 않습니다.

## 3. 규격 확인 (2026-10 기준)

MCP 규격은 2026-07-28판이 최신이고, 이전(2025-11-25)과 다릅니다. 설계에 영향이 큰 부분만 적습니다. 구현 직전에 원문을 다시 확인합니다.

| 항목 | 2025-11-25 | 2026-07-28 | 설계에 주는 영향 |
|---|---|---|---|
| 세션 | `initialize`/`initialized` + `Mcp-Session-Id` | **폐지.** 요청마다 버전, 클라이언트, 능력을 `_meta`에 실음. `server/discover`는 선택 | 지금 워커는 옛 방식. **두 방식을 모두 말해야 함**: 새 방식을 먼저 시도하고, 서버가 옛 방식만 알면 되돌아감 |
| 헤더 | - | Streamable HTTP 요청에 `Mcp-Method`, `Mcp-Name` 필수 | 워커 요청에 추가 |
| 목록 | 변경 알림 | `tools/list`에 `ttlMs`, `cacheScope`, 결정적 정렬. 알림은 `subscriptions/listen` 스트림 | 목록 변경 감지는 **주기적 재조회 + 지문 비교**를 기본으로 하고, 스트림은 선택 |
| 서버가 묻는 일 | 열린 스트림 | 여러 번 왕복(`input_required`) | 도구가 `input_required`를 돌려주면 **사람에게 묻는 승인**으로 연결(5.2절) |
| 인증 발견 | 보호 자원 메타데이터(RFC 9728), 인증 서버 메타데이터(RFC 8414) | 같음 + 응답의 `iss` 검증(RFC 9207), 클라이언트 자격증명은 발급 서버에 묶임 | 발견 순서와 `iss` 검증을 구현 |
| 클라이언트 등록 | DCR 또는 CIMD(권장) | **DCR은 폐지 예정, CIMD가 기본** | 아래 7장 결정 3 |
| 도구 주석 | `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint` | (확인 필요) | **주석은 힌트일 뿐 신뢰하지 않습니다**(4.3절) |

## 4. 설계

### 4.1 연결 레지스트리: 종류만 다른 같은 모양

`api_connections`를 그대로 두고 **종류(kind)와 상태**를 더합니다. 새 테이블을 늘리지 않고 같은 방식으로 다룹니다.

- `api_connections.kind`: `http` (기본, 지금과 동일), `mcp`.
- `api_connections.auth_kind`에 `oauth` 추가.
- 상태 열: `health` (`unknown`, `ok`, `auth_needed`, `unreachable`, `changed`), `health_checked_at`, `health_detail`.
- 모델 제공사는 `llm_providers`를 유지하고 `purpose`에 `decision`을 추가합니다(3d). 화면에서는 같은 **Connections** 안에서 같은 순서(주소 → 인증 → 시험 → 사용)로 보입니다.

### 4.2 MCP 도구 발견과 등록

새 테이블 `mcp_tools`: 연결별 도구 목록의 사본.

| 열 | 뜻 |
|---|---|
| `connection_id`, `tool_name` | 기본키 |
| `description`, `input_schema` | 서버가 알려준 것 (`tools/list`) |
| `server_hints` | 서버가 보낸 주석(`readOnlyHint` 등). **참고용** |
| `risk` | `read`, `write`, `physical`, `unknown`. 사람이 확인한 값 |
| `risk_source` | `default`, `hint`, `operator` |
| `approval` | `none`, `required` |
| `fingerprint` | 이름 + 설명 + 스키마의 해시 |
| `registered_function_id` | 능력으로 등록되었으면 연결된 함수 |
| `status` | `new`, `registered`, `changed`, `removed` |

흐름:
1. 연결 추가: 주소를 붙여넣음 → 워커가 발견/호출 시험(`provider_probes`와 같은 큐 방식) → 성공하면 `tools/list`를 전부 가져와 `mcp_tools`에 `new`로 저장.
2. 화면에 도구 목록과 **위험 등급**을 보여주고, 사람이 확인하며 체크한 도구만 `functions`(`handler='mcp_call'`)로 등록. 이미 있는 등록 경로(`mcp_connection_id`, 도구 이름 고정)를 그대로 씁니다.
3. 에이전트에게 권한을 주는 것은 지금과 같습니다(Canvas 또는 Agents).

### 4.3 위험 등급: 서버의 말을 믿지 않는다

서버가 보낸 주석은 서버가 거짓말할 수도, 실수할 수도 있습니다. 그래서 **등급은 규칙이 정하고 사람이 확인**합니다.

- 기본값은 **`unknown` + 승인 필요**입니다. 사람이 확인하기 전에는 등록 자체가 안 됩니다.
- 주석 `readOnlyHint=true`이면 등급 후보를 `read`로 **제안**만 합니다. `destructiveHint`이거나 이름/설명에 동작 동사(예: start, stop, move, write, delete, send, set, actuate)가 있으면 `write` 또는 `physical` 후보로 제안합니다. 제안 규칙은 데이터(`mcp_risk_rules`)이고 관리자가 고칠 수 있습니다.
- 등급별 기본 승인: `read` → 없음, `write` → 필요, `physical` → 필요(결재 규칙에서 별도 역할 지정 가능), `unknown` → 등록 불가.
- 승인 요청에는 1단계의 판단 기록이 그대로 쌓이므로, 사람이 어떤 도구 호출을 허락/거절했는지가 학습 데이터가 됩니다.

### 4.4 인증 (OAuth 포함)

방식 선택은 **발견 결과**로 정합니다. 사용자는 주소만 넣습니다.

1. 인증 없이 호출 → `401` + `WWW-Authenticate`(`resource_metadata`) 또는 `/.well-known/oauth-protected-resource` 조회 → 인증 서버 주소 → `/.well-known/oauth-authorization-server`(또는 OIDC) 조회.
2. 인증 서버가 있으면 `oauth`: 인증 코드 + PKCE(S256), `resource` 지시자(RFC 8707), 응답의 `iss` 검증.
3. 인증 서버가 없고 키만 받는 서버면 기존 `authorization`/`x-api-key`.

대시보드는 이미 웹 서버(`src/web.rs`)이므로 **콜백 경로 하나**(`/oauth/callback`)를 추가합니다. 그 안에서 하는 일은 `state` 확인 후 코드를 PG에 넘기는 것까지이고, 토큰 교환은 워커가 합니다(외부 I/O는 워커). 토큰은 `api_connection_secrets`에 암호화 저장, 갱신은 워커가 만료 전에 합니다. 갱신에 실패하면 `health='auth_needed'`가 됩니다.

### 4.5 연결 상태와 변경 감지

워커가 주기적으로(기본 15분, 연결별 조정) 가볍게 확인합니다.

- 도달 가능한가, 인증이 유효한가, `tools/list`의 지문이 같은가.
- **도구 지문이 바뀌면** 해당 도구를 `changed`로 표시하고 **등록된 함수를 일시 중지**한 뒤 승인 요청을 만듭니다(도구 설명이 몰래 바뀌는 공격을 막는 지점). 사람이 변경 내용을 보고 재승인해야 다시 켜집니다.
- 연결이 끊기면(`unreachable`/`auth_needed`) 그 도구를 쓰려는 작업은 **실패 대신 대기**하고 홈의 "Needs attention"에 나타납니다.

### 4.6 들어오는 이벤트

외부 시스템이 먼저 알리는 경우(센서 경보, 새 문서)를 위한 **수신 주소**입니다.

- 새 테이블 `inbound_sources`(이름, 비밀 서명값, 대상 에이전트, 목표 템플릿, 사용 여부)와 `inbound_events`(수신 시각, 서명 검증 결과, 본문, 처리 상태).
- 대시보드 웹 서버에 `POST /inbound/{source}` 하나 추가. **HMAC 서명 검증 필수**, 본문 크기 제한, 연결당 분당 한도. 검증을 통과한 것만 큐에 넣습니다.
- 규칙에 따라 작업을 시작하거나(`goal` 템플릿에 본문 일부 삽입), 승인 요청으로 보냅니다. 본문은 **데이터로만** 쓰이고 지시문으로 해석하지 않습니다(프롬프트 주입 방지: 템플릿 자리표시자에만 들어가고 길이 제한).
- MCP 알림 구독은 이 큐로 같은 방식으로 들어옵니다(후순위, 3e의 선택 항목).

### 4.7 모델 제공사와 판단 모델

- **채팅/임베딩**: 주소 + 키 → 연결 시험(있음) → **모델 목록 조회**(`/models`) → 고르면 가격표 자동 입력(알려진 모델은 내장 표, 모르면 0과 경고) → 예산 상한이 바로 동작.
- **판단 모델**(`purpose='decision'`): 주소 + 키(선택) → `/health` → 사용 가능한 체크포인트와 버전 표시. 공식 `laya-serve`와 같은 요청 형식만 지원. **연결해도 판단 지점의 위임 모드는 `off`가 기본**이고, 지점별 토글은 6단계에서 켭니다. 3단계는 연결과 상태 확인까지만 합니다.

공통: 조각마다 별도 PR. `fn_selftest` 사례, 로컬 CI SQL 순서 재현, 브라우저 테스트, 스크린샷 확인 후 병합. 규격 관련 코드는 구현 직전 원문 재확인. 3a의 목 MCP 서버는 기존 `/mock` 방식처럼 대시보드 웹 서버에 내장하되 시험용 환경 변수 뒤에 둡니다.

## 7. 정해야 할 것 (권장안 포함)

1. **MCP 규격 지원 범위.** 권장: 2026-07-28(무상태)을 우선 시도하고 2025-11-25(세션)로 되돌아가는 **양쪽 지원**. 옛 HTTP+SSE 전송은 지원하지 않음.
2. **위험 등급 기본값.** 권장: 확인 전에는 등록 불가(`unknown`), `write`/`physical`은 기본 승인 필요. 서버 주석은 제안에만 사용.
3. **OAuth 클라이언트 등록.** 권장: **CIMD를 우선**(Allgres가 공개 주소의 메타데이터 문서를 내놓는 방식은 공개 주소가 필요함), 인증 서버가 CIMD를 지원하지 않으면 DCR로 되돌아가고, 둘 다 안 되면 사람이 클라이언트 ID를 직접 입력. 공개 주소가 없는 로컬 설치는 DCR 또는 직접 입력이 현실적.
4. **도구 변경 시 동작.** 권장: 변경된 도구는 자동 중지 + 재승인. (대안: 알림만. 보안상 권장하지 않음.)
5. **들어오는 이벤트.** 권장: 3e로 미루고 HMAC 서명 필수. 본문은 목표 템플릿의 자리표시자에만 삽입.
6. **들어오는 이벤트의 외부 접근.** 대시보드는 기본이 로컬 바인딩입니다. 수신 주소를 외부에 열지는 배포하는 사람이 정하고(역방향 프록시), 문서에 경고와 예시를 적습니다.

## 8. 하지 않는 것

- PG 안에서 MCP 서버나 모델을 실행하지 않습니다.
- stdio 서버를 Allgres가 직접 띄우지 않습니다.
- 서버의 도구 주석을 신뢰 근거로 쓰지 않습니다.
- 판단 모델에 일을 위임하는 토글은 만들지 않습니다(6단계).
