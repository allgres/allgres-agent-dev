# 5단계 설계: 대화방과 팀 협업

> 상태: **5a, 5b 구현됨, 5c 중 `auto` 모드와 안전장치(취소 포함) 구현됨** ([rooms.md](rooms.md)). 여러 소속, 팀 창구, 공유 지식 범위, 협업 가시성도 구현됨([teams.md](teams.md)). 캔버스의 점선 표시와 방 요약의 자동 저장은 하지 않았습니다. `auto` 방은 총괄·0보다 큰 비용 한도·턴 50 이하·깊이 6 이하·모든 에이전트 모델에 가격이 있을 때만 켤 수 있고 확정마다 다시 확인합니다. 5b에서 바뀐 점: 봇이 부르는 것은 위임과 같은 규칙으로 막습니다(부르는 쪽이 받는 쪽에 대한 `agent` 권한이 있어야 함). 같은 두 에이전트가 6턴 연속 주고받으면 멈춥니다("새 정보 없음"을 글로 판정하지 않고 연속 호출 횟수로 단순하게 판정). 사람이 확정한 기록에는 방에서 사람이 쓴 글을 넣지 않습니다. 5a에서 바뀐 점: 팀 메시지를 "기본 방"으로 옮기는 일(8장 1번)은 하지 않고 방을 **옆에 추가**했습니다(기존 팀 메시지와 `@` 동작은 그대로). 방이 자리 잡은 뒤에 합칩니다. 스크립트로 정해진 답을 하는 모의 모델은 봇끼리 대화하는 5b에서 만듭니다(5a의 시험은 지금의 모의 모델이 답하는 것으로 충분했습니다). [improvement-plan.md](improvement-plan.md)의 5단계에 "봇들이 대화방에서 서로 소통하고 역할을 맡는 것"을 더해 구체화했습니다. 8장의 결정을 확인한 뒤 5a부터 구현합니다. (요청 배경: Grok Bot의 그룹 대화처럼 봇끼리 소통하고 방으로 묶고 역할을 주는 기능을, 사람이 태스크를 확정하는 방식과 봇이 자동으로 확정하는 방식 둘 다 선택할 수 있게.)

## 1. 목표와 범위

1. **대화방**: 사람과 에이전트 여러 명이 한 방에서 대화합니다. 방마다 에이전트에게 **역할**을 줍니다.
2. **봇끼리 소통**: 방 안에서 에이전트가 서로를 불러 일을 넘깁니다. 항상 한도 안에서만 합니다.
3. **태스크 확정 방식을 방마다 고름**: 사람이 확정하거나, 봇이 제안하고 사람이 확인하거나, 봇이 스스로 확정하고 진행합니다.
4. 계획서의 나머지 5단계 항목: 여러 소속, 팀 창구, 공유 지식 범위, 협업 가시성.

원칙은 그대로입니다. 상태와 제어는 PostgreSQL이 갖고, 에이전트의 일은 지금처럼 **작업(task)** 으로 돌며 위임 상한, 도구 위험 등급, 예산, 승인이 그대로 적용됩니다. 방은 새로운 실행 방식이 아니라 **작업을 시작하고 모으는 자리**입니다.

## 2. 지금 있는 것 (코드에서 확인)

| 있는 것 | 위치 | 대화방에 쓰는 법 |
|---|---|---|
| 팀 메시지: 한 개의 공용 채널, `@agent`로 부르면 그 에이전트의 대화 세션이 시작됨 | `channel_messages`, `fn_messenger_post` | 방의 원형. 이것을 "기본 방"으로 옮깁니다 |
| 에이전트의 `delegate` 행동, 하위 작업, `waiting_children` | `fn_submit_result` | 봇끼리 넘기는 수단. 이미 깊이 한도(`max_delegation_depth`)와 세션당 작업 수 한도(`max_session_tasks`)가 있음 |
| 위임 상한 | `canvas_superiors`, `agent_has_permission` | 방 안에서도 같은 상한이 적용됨 |
| 도구 위험 등급, 승인 | 3a, `requires_approval` | 방 안의 작업에도 그대로 |
| 판단 기록 | `decision_records` (`decided_by`: human, rule, llm, laya) | 태스크 확정을 판단 지점으로 등록 |
| 그룹(팀) | `agent_groups`, `agent_group_members` (에이전트당 한 그룹만) | 방을 팀에서 열 수 있음. 여러 소속은 5c |

**없는 것**: 여러 개의 방, 방 안의 역할, 에이전트가 방에 글을 남기는 길, 방 단위 한도, 태스크 확정을 방이 정하는 설정.

## 3. 방과 역할

새 테이블(이름은 구현 때 확정):

| 테이블 | 내용 |
|---|---|
| `rooms` | 이름, 목적(한 줄), `mode`(`manual`/`assisted`/`auto`), `lead_agent_id`, 한도(`max_turns`, `max_cost_usd`), 상태(`open`/`closed`), 만든 사람 |
| `room_members` | 방, 구성원(사람 또는 에이전트), 역할 |
| `room_roles` | 역할 정의: 이름, 설명, **지시문**(그 역할일 때 에이전트에게 더해 주는 말). 예: 총괄, 검토자, 구현 담당, 기록 담당 |
| `room_messages` | 방, 글쓴이(사람/에이전트/시스템), 내용, 부른 구성원, 연결된 세션과 작업, 턴 번호, 종류(`say`/`task_proposal`/`task_started`/`notice`) |

**역할은 권한이 아닙니다.** 역할은 "이 방에서 무엇을 맡는가"를 에이전트에게 알려 주는 지시문일 뿐이고, 도구와 데이터 권한은 지금처럼 에이전트의 권한(`permissions`)과 위임 상한이 정합니다. 역할을 "관리자"로 지정해도 권한이 늘어나지 않습니다. 그래서 역할 배정은 안전한 설정이고, 사람이 방을 열 때 에이전트를 넣으며 정합니다.

방은 사람이 만들거나 캔버스의 팀에서 "이 팀으로 방 열기"로 만듭니다. 방의 구성원은 사람이 정합니다. 에이전트가 스스로 방에 들어오거나 다른 에이전트를 데려올 수 없습니다.

## 4. 한 번의 대화가 도는 방식

1. 방에 글이 올라옵니다(사람의 글, 또는 에이전트의 글).
2. 그 글이 **부른** 구성원이 정해집니다: `@이름`으로 부른 구성원, 없으면 총괄. `manual` 방에서는 **사람의 글만** 구성원을 부릅니다.
3. 부른 에이전트마다 **작업** 하나가 시작됩니다. 목표에는 방의 최근 글(요약 포함), 그 에이전트의 역할 지시문이 들어갑니다. 방의 글은 **데이터**로만 전달되고 지시문으로 해석하지 않습니다(들어오는 이벤트와 같은 방식).
4. 작업이 끝나면 최종 답이 에이전트의 글로 방에 올라옵니다. `assisted`/`auto` 방에서 그 글이 다른 구성원을 `@`로 부르면 2번으로 돌아갑니다. 이것이 봇끼리의 소통입니다.
5. 아무도 부르지 않거나 한도에 닿으면 멈춥니다.

한 방의 모든 작업은 방에 묶여 비용과 턴 수가 합산됩니다. 활동 화면과 감사 기록에는 지금처럼 개별 작업으로 보입니다.

## 5. 태스크를 누가 확정하나: 방의 모드

"태스크를 확정한다"는 것은 방의 논의 결과를 **실제로 진행할 일(작업)** 로 만드는 것입니다. 방마다 정합니다.

| 모드 | 봇끼리 소통 | 태스크 확정 |
|---|---|---|
| **manual** (기본) | 하지 않음. 사람이 부를 때만 봇이 답함 | 사람이 직접. 어떤 글이든 "태스크로 만들기"를 눌러 담당자와 목표를 정함 |
| **assisted** | 함. 한도 안에서 서로 부르며 논의 | 총괄이 논의를 모아 **태스크 제안**을 올림 → 사람이 확인(승인)하면 시작 |
| **auto** | 함 | 총괄이 제안하고 **방이 스스로 확정**해 바로 시작. 사람은 나중에 보고 끌 수 있음 |

모드는 방 단위 설정이고 사람(관리자)만 바꿉니다. 언제든 `manual`로 내리면 즉시 봇끼리의 소통이 멈춥니다. `auto`는 방을 만들 때 기본으로 꺼져 있고, 관리자가 방마다 켭니다.

**판단 기록과의 관계.** 태스크 확정을 판단 지점(`room_task_confirmation`)으로 등록합니다.
- 사람이 확정하면 기존대로 `decided_by='human'`, 상황·질문·답이 Laya 형식으로 쌓이고 정답 데이터가 됩니다.
- `auto`에서 방이 확정하면 `decided_by='llm'`으로 기록합니다. 이 기록은 **정답으로 쓰이지 않습니다**(사람의 판단만 정답이라는 원칙이 그대로 유지됨). 나중에 사람이 검토하며 정답으로 고칠 수는 있습니다.
- 나중에 6단계에서 판단 모델에 위임을 켜면, 이 지점도 지점별 토글의 한 항목이 됩니다.

## 6. 안전장치 (자동 모드에서 특히)

| 위험 | 막는 방법 |
|---|---|
| 봇끼리 끝없이 대화 | 방별 `max_turns`(기본 12), 한 사슬의 깊이 한도(기존 `max_delegation_depth`), 같은 두 구성원이 새 정보 없이 주고받으면 중단(마지막 두 글의 유사도가 아니라 **연속 N번 같은 쌍의 호출**로 단순하게 판정) |
| 비용 폭주 | 방별 `max_cost_usd`(기본은 켜짐). 넘으면 방이 `closed`가 되고 알림을 남김. 모델 가격이 없는 모델은 한도를 셀 수 없으므로 `auto` 방에서는 **가격 없는 모델의 에이전트를 넣지 못하게** 함 |
| 권한 확대 | 역할은 권한이 아님. 위임 상한과 도구 위험 등급은 방과 무관하게 적용. 쓰기·장비 동작 도구는 `auto`에서도 매번 사람 승인 |
| 방의 글로 지시 주입 | 글은 데이터 블록으로만 전달. 에이전트의 글이 다른 에이전트의 **권한이나 목표를 바꾸지 못함** |
| 사람이 모르는 사이 진행 | 방에 시작된 작업과 확정이 모두 `notice` 글로 남고, 홈의 "진행 중"에 보임. `auto`에서 확정된 태스크는 되돌리기(취소) 버튼이 있음 |
| 에이전트가 방을 마음대로 키움 | 구성원 추가, 모드 변경, 한도 변경은 사람만 |

## 7. 계획서의 나머지 5단계 항목

- **여러 소속 (5c)**: 에이전트가 여러 그룹에 속할 수 있게 `agent_group_members`의 기본키를 `(agent_id, group_id)`로 바꾸고 `is_primary`를 둡니다. **권한 상한과 비용 책임은 주 소속 기준**, 보조 소속은 업무가 들어오는 길과 방 열기만 엽니다. 캔버스는 보조 소속을 점선으로 보여 줍니다.
- **팀 창구 (5c)**: 팀 단위로 일을 받는 접수구. 다른 팀은 에이전트가 아니라 창구에 맡기고, 팀 안에서 담당자가 정해집니다(지정된 접수 에이전트, 또는 사람 배정. 사람 배정은 판단 지점이라 기록이 쌓임). 창구에 맡겨도 맡기는 팀이 창구의 상한 이상을 얻지 못합니다.
- **공유 지식 범위 (5d)**: 기억과 지식을 에이전트·팀·조직 세 범위로 나누고 읽기와 쓰기 권한을 따로 둡니다. 방의 요약도 팀 범위의 기억으로 남길 수 있습니다.
- **협업 가시성 (5e)**: 다른 팀에 맡긴 일의 진행과 결과가 맡긴 쪽에 보이고, 결과에는 출처와 근거가 따라갑니다.

## 8. 정해야 할 것 (권장안 포함)

1. **기본 방.** 권장: 지금의 팀 메시지를 "기본 방"(`manual`)으로 옮깁니다. 기존 글과 `@` 동작은 그대로입니다.
2. **역할은 지시문일 뿐 권한이 아님.** 권장: 위와 같음.
3. **기본 한도.** 권장: `max_turns` 12, `max_cost_usd` 1.00. 방마다 조정.
4. **`auto` 모드의 조건.** 권장: 관리자만 켤 수 있고, 가격이 있는 모델의 에이전트만 구성원이 될 수 있고, 한도가 반드시 있어야 합니다.
5. **봇이 확정한 기록.** 권장: `decided_by='llm'`으로 기록하되 정답 데이터에서 제외.
6. **봇이 방을 만들 수 있나.** 권장: 아니요. 방 생성과 구성원 변경은 사람만.

| 조각 | 내용 | 완료 기준 |
|---|---|---|
| 5a | 방, 구성원, 역할, 방 메시지, 기본 방으로 이전, `manual` 모드(사람이 부를 때만), 태스크로 만들기, 방 화면 | 기본 방에서 기존 `@` 동작이 그대로. 방 두 개를 만들어 역할이 다른 에이전트 둘을 넣고 각각 부름. 방의 글이 데이터로만 전달됨 |
| 5b | 봇끼리의 소통(`assisted`), 태스크 제안과 사람의 확인, 판단 기록, 한도(턴, 비용) | 총괄이 둘의 논의를 모아 제안을 올리고, 사람이 승인하면 작업이 시작되고 기록이 정답으로 쌓임. 한도에 닿으면 멈추고 알림 |
| 5c | `auto` 모드와 안전장치(반복 중단, 가격 없는 모델 거부, 취소), 여러 소속, 팀 창구 | 자동 방에서 확정이 `llm`으로 기록되고 정답에서 빠짐. 위험 도구는 자동 방에서도 승인을 기다림. 매트릭스 조직 시나리오 |
| 5d | 공유 지식 범위 | 팀 범위 기억을 같은 팀만 읽음 |
| 5e | 협업 가시성 | 다른 팀에 맡긴 일의 진행이 맡긴 쪽에 보임 |

공통: 조각마다 별도 PR, `fn_selftest` 사례, 로컬 CI SQL 순서 재현, 브라우저 테스트, 스크린샷 확인 후 병합. 방의 모의 시나리오를 위해 **스크립트로 정해진 답을 하는 모의 모델**이 필요합니다(지금의 모의 모델은 최종 답만 합니다). 이것은 테스트 전용 `/mock/*` 안에 둡니다. 이것이 있으면 3a에서 검증하지 못한 "에이전트가 MCP 도구를 호출하는 장면"도 시험할 수 있습니다.

## 10. 하지 않는 것

- 에이전트가 스스로 방을 만들거나, 구성원을 데려오거나, 한도를 바꾸는 것.
- 역할로 권한을 주는 것.
- 방 안에서 다른 조직의 에이전트를 직접 부르는 것(5c의 팀 창구를 거칩니다).
- 외부 서비스의 봇을 방에 직접 넣는 것(MCP 서버를 능력으로 연결하는 방식을 그대로 씁니다).
