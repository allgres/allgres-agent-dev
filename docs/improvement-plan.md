## 3. 핵심 원칙과 운영 규칙

**제품 목표 (v6):** 사용자가 한 문장으로 일을 맡기면, 상시 켜진 에이전트가 기억하고, 정해진 때 스스로 실행하고, 필요할 때만 승인을 받는다.

### 3.1 원칙

이 원칙은 모든 단계의 설계 판단 기준입니다. 원칙과 충돌하는 설계는 채택하지 않습니다. v6에서도 Allgres 원칙은 그대로입니다. 상태와 제어 결정은 PostgreSQL이 갖고, Rust 워커는 외부 I/O만 하며, 보안 경계는 SQL 규칙이 정하고, 모델은 판단하지 않습니다.

#### P1. Postgres is all you need
- Allgres를 운영하는 데 필요한 것은 **PostgreSQL 하나**입니다. 별도의 Node.js, Python, Redis, 큐 서버, 웹서버 서비스를 요구하지 않습니다(README의 기존 원칙).
- 브라우저 화면은 JS(React)로 만들지만 **빌드할 때만** Node를 쓰고, 운영 중에는 Rust 웹서버가 결과 파일을 내보냅니다.

#### P2. PG는 상태와 제어 결정을 소유하고, 외부 I/O는 Rust 워커가 한다
- 조직, 사람, 권한, 결재, 작업 상태, 판단 기록, 감사 기록은 모두 PG 테이블에 있습니다.
- 외부 호출(LLM, 임베딩, 판단 모델, MCP, HTTP API)은 Rust 백그라운드 워커가 하고, 외부 호출은 DB 트랜잭션 밖에서 일어납니다(기존 원칙).

#### P3. PG 안에는 어떤 모델도, 외부 서버 프로세스도 없다
- LLM, 임베딩 모델, 판단 모델(Laya, Jev)은 모두 **외부 프로바이더**로 호출합니다.
- MCP 서버는 로컬용이든 원격용이든 모두 **PG 밖**에서 돕니다.
- 모델 학습도 PG 밖에서 합니다.

#### P4. PG로 안 되는 능력은 MCP로 확장한다
- PG의 function, procedure(그리고 기존 `http_get` 같은 단순 HTTP 핸들러)로 되는 일은 PG 안에서 합니다.
- 그 외의 능력(웹 리서치, 장비 제어, 전력 모니터링, 사내 시스템 연동 등)은 **MCP 서버를 연결**해서 얻습니다.
- 어떤 능력이 PG에서 오든 MCP에서 오든, **권한, 승인, 기록 규칙은 PG가 똑같이 적용**합니다.

#### P5. 보안 경계는 규칙이 결정한다
- 권한 상한, 위임 가능 대상, 실행 규칙(허용/승인/거부)은 SQL 규칙이 최종 결정합니다.
- 판단 모델(Laya)은 이 규칙이 허용하는 범위 안에서만 선택을 맡습니다. 높은 확신이 실행 권한이 되지는 않습니다(Laya 공식 문서도 같은 입장).

#### P6. 모든 판단은 사람 기준으로 정상 동작하고, Laya는 지점별 위임이다
- 판단 지점의 기본 결정자는 **사람**(과 기존 규칙)입니다.
- Laya를 연결하고 특정 판단 지점에서 켜면, **그 지점만 사람 대신 Laya에게 위임**합니다. Laya가 확신이 낮다고 표시하면 그 건은 다시 사람에게 돌아갑니다.
- Laya가 없거나, 꺼져 있거나, 응답하지 않아도 모든 기능은 정상 동작합니다.

#### P7. 판단 기록은 항상 쌓는다 (v6 개정)
- Laya 사용 여부와 상관없이 판단이 일어날 때마다 기록합니다.
- **[v6 개정]** 운영 감사 기록과 Laya 학습용 표현을 분리합니다. 결정 기록에는 요청 사본, 규칙 버전, 이유를 남기고 **2단계부터 저장**합니다. Laya 공식 학습·평가 형식(JSONL의 `state`, `questions`, `expected`)으로 바꾸는 일은 5단계의 "Laya 변환과 내보내기"에서 합니다. v5의 "기록을 처음부터 Laya 형식 그대로 쌓아 내보낼 때 변환이 필요 없게 한다"는 요구는 폐기했습니다.
- PG는 기록을 **담아뒀다가 넘겨주는 역할만** 합니다. 모델 계산, 기준선 재계산, 학습은 하지 않습니다.

#### P8. Laya는 공식 표준만 사용한다
- 추론은 공식 `laya-serve`(HTTP), 학습은 공식 `laya-train`, 평가는 공식 `laya-evals`, 도입 절차는 공식 단계적 도입 가이드를 따릅니다.
- Laya 쪽에 새 래퍼, 학습 컨테이너, 전용 MCP 서버를 만들지 않습니다.

#### P9. 실제 업무 흐름으로 검증한다
- 모든 단계는 6장에 적힌 그 단계의 **완료 정의**를 통과해야 완료입니다. **[v6 개정]** v5의 "12장 시나리오를 통과해야 완료"는 v6의 단계별 완료 정의로 바뀌었습니다. 12장 시나리오는 그대로 둡니다(12장 머리말 참고).
- 새 요구가 생기면 먼저 시나리오로 시뮬레이션해서 막히는 곳을 찾고, 그다음에 구현합니다.

#### P10. 쉽고 직관적이어야 한다
- 기준은 "설명서 없이 처음 쓰는 사람이 끝까지 해낼 수 있는가"입니다. 11장의 UX 원칙을 따릅니다.

#### P11. 모델 출력은 항상 초안이다 (v6 신규)
- 서버(SQL)가 검증하고 정규화하며, 정규화된 내용을 사용자가 확인합니다.
- 모델의 성공률과 관계없이 이 규칙은 바뀌지 않습니다.

### 3.2 운영 규칙 (v6 신규)

- **단계는 릴리스가 아니다.** 소유자가 한 브랜치, 한 PR로 내기로 했으므로, 단계는 브랜치 안의 게이트입니다. 리뷰어가 게이트를 검증해야 다음 단계 커밋을 시작합니다.
- **게이트 통과는 커밋 SHA에 결합한다.** 다음 영역이 바뀌면 해당 게이트 회귀를 다시 돌립니다.
  - 대상: `sql/`, `src/`, `web/`, `scripts/`(설치·기동·bootstrap·run_sql_tests), Dockerfile·compose·`packaging/`·`cnpg/`, `tests/`, CI 워크플로, `allgres.control`, 업그레이드 스크립트
  - 경로는 재검증을 시작하는 최소 조건일 뿐입니다. 영향이 불분명하면 재실행합니다.
  - 테스트, CI, 러너가 바뀌면 모든 게이트를 다시 돌립니다.
  - 최종 PR HEAD에서 1~3a 전체 회귀를 한 번 더 돕니다.
- **공통 검증 규칙**
  - 테스트 준비에는 SQL을 써도 됩니다. 하지만 성공 상태를 `fn_run_schedules`, claim, complete를 직접 불러 만들면 안 됩니다.
  - 확인 경로: RPC/채팅 입력 → 실제 워커 → executor → 결과 저장과 전달
  - 변이는 격리 환경에서 하나씩 적용합니다. 정상 통과 → 변이 시 실패 → 복원 후 통과를 같은 테스트로 증명합니다. 컴파일 실패는 변이 검증으로 인정하지 않습니다.

### 4.2 구조적 한계 (확장성)

| 영역 | 현재 구조 | 커버하지 못하는 상황 |
|---|---|---|
| **사람 쪽 조직** | 사용자 역할은 `admin`과 `user` 둘뿐(`sql/operator_accounts_and_chat.sql` 423행). 승인 요청 테이블 `human_approvals`(`sql/control_plane.sql` 1616행)에는 작업, 상태, 내용, 기한만 있고 **누가 결정해야 하는지가 없음** | 결재선(예산은 본부장, 법무 검토는 법무팀), 대리 결재, 기한 초과 시 상위자 상정. 그리고 **Laya가 "어떤 사람의 어떤 판단"을 대신하는지 정의할 수 없음** |
| **에이전트 소속** | `agent_group_members`의 기본키가 `agent_id`라서 에이전트는 그룹 하나에만 속함(`sql/canvas.sql` 36행). 그룹은 `team`, `division`, `project`로 중첩 가능 | 매트릭스 조직, 여러 팀이 함께 쓰는 공용 에이전트(법무 검토, 디자인), 팀에서 구성원을 빌려오는 프로젝트 팀 |
| **팀 간 협업** | 위임 대상이 **에이전트 이름**. 위임 권한은 `permissions`의 `resource_type='agent'`이고, 상한은 위임 선을 거슬러 올라가며 계산(`canvas_superiors`, `sql/canvas.sql` 100행) | "영업팀에 요청"처럼 팀 창구로 맡기기. 팀이 늘면 팀끼리 잇는 선이 N²개로 늘어남. 팀 내부 담당자가 바뀌면 다른 팀의 선을 모두 다시 그려야 함 |
| **지식 공유** | 기억 `agent_memories`가 `agent_id`별로 저장됨(`sql/control_plane.sql` 1293행) | 팀이나 조직 공용 지식(브랜드 가이드, 지난 캠페인 결과)을 여러 에이전트가 함께 읽고 갱신하는 것 |
| **판단 지점** | 판단 지점이라는 개념이 없음. 판단은 승인 요청, 변경 제안 등 기능마다 흩어져 있음 | 판단을 일관되게 기록하거나, 조직별 새 판단(채용 1차 심사, 계약 위험 분류)을 추가하는 것 |
| **능력 종류** | 함수 핸들러는 `http_get`, `plpgsql`, `mcp_call` 세 가지(`sql/control_plane.sql` 2155행). 에이전트가 직접 만들 수 있는 건 `plpgsql`뿐이고 변경 제안 승인을 거침 | MCP 도구별 위험 등급이 없음. 조회 도구와 물리 동작 도구가 같은 서버에 있으면 구분 없이 다뤄짐 |
| **들어오는 이벤트** | 일정(`schedules`)으로 주기 실행은 가능. MCP는 Allgres가 **호출만** 함 | 외부에서 이상을 알려주면 작업을 시작하는 방식(전력 이상 알림 등) |
| **조직 단위** | DB 하나가 조직 하나(조직 구분 키 없음) | 한 설치에서 여러 회사나 고객사를 나눠 운영하는 것. DB를 나누는 방식으로 대응 가능하므로 우선순위 낮음 |
| **규모** | PG 하나 + 백그라운드 워커 | 에이전트 수백 개, 동시 작업 수천 개에서의 동작은 검증된 적 없음 |

### 4.3 사용성 문제 (화면 점검과 시뮬레이션에서 확인)

- 연결 설정이 설정 화면 한 곳에 폼으로 나열돼 있음: 모델 프로바이더, API 연결, 함수, 사용법 문서. 무엇을 먼저 해야 하는지 안내가 없음.
- MCP 연결이 OAuth를 요구하면 사용자가 인증 정보를 직접 준비해야 함.
- 능력(함수, 사용법 문서)을 만드는 경로가 화면에서 잘 드러나지 않음. "리서치 스킬은 어디서 만드나"에 답하기 어려움.
- 예산 상한(`max_cost_usd`)은 모델 가격이 입력돼 있어야 동작하는데, 가격 입력이 따로 떨어져 있음.
- 용어가 화면마다 다름. 위임, 권한, 능력, 스킬, 함수, 도구가 섞여 있음.

## 5. 목표 구조

최종적으로 도달할 구조입니다. v6에서는 이 구조를 6장의 순서대로 채웁니다. 조직(사람, 역할, 팀, 소속), 판단 지점, Laya 형식 내보내기, 팀·조직 범위 공유 지식은 5단계입니다. 판단 기록은 운영 감사 기록으로 쌓고, Laya 형식은 5단계의 변환에서 만듭니다(3.1절 P7).

```
                       ┌──────────────────────────────────────────────┐
  사람(브라우저) ─────▶ │ Allgres = PostgreSQL + Allgres 확장           │
                       │                                              │
                       │  PG가 소유하는 것                             │
                       │   · 조직: 사람, 역할, 팀, 에이전트, 소속      │
                       │   · 권한과 상한, 실행 규칙, 결재 규칙         │
                       │   · 작업 상태, 승인함, 감사 기록              │
                       │   · 판단 지점 정의와 판단 기록(Laya 형식)     │
                       │   · 능력 목록: PG 함수, 사용법 문서, MCP 도구  │
                       │   · 공유 지식(에이전트/팀/조직 범위)          │
                       │                                              │
                       │  Rust 워커가 하는 것                          │
                       │   · 웹서버(대시보드, 캔버스)                  │
                       │   · 모든 외부 호출과 재시도                   │
                       │   · 들어오는 이벤트 받기                      │
                       └───────────────┬──────────────────────────────┘
                                       │ HTTP
        ┌───────────────┬──────────────┼───────────────┬────────────────────┐
        ▼               ▼              ▼               ▼                    ▼
   LLM 프로바이더   임베딩 프로바이더  판단 모델        MCP 서버들            일반 HTTP API
   (chat)          (embedding)       (decision)      리서치, 기계제어,
                                     laya-serve      전력모니터링, 사내
                                     또는 Jev        시스템, 로컬 MCP 중계 …

   PG 밖, Allgres와 별개:  Laya 학습(공식 laya-train), 평가(공식 laya-evals)
                           ← Allgres가 내보낸 공식 형식 JSONL을 입력으로 사용
```

## 6. 단계별 계획 (v6)

순서: **1 → 2 → 3a → 3b → 4 → 5.** 2단계 진행과 함께, 1단계 진행 중에 프롬프트 스파이크(6.2절 끝)를 병행합니다. 단계는 릴리스가 아니라 한 브랜치 안의 게이트이며, 리뷰어가 게이트를 검증해야 다음 단계 커밋을 시작합니다(3.2절).

v5의 0~6단계가 v6에서 어디로 갔는지는 18장에 정리했습니다.

### 6.1 1단계: 설치·복구·스케줄 기반 (검증 조건으로 기술)

**목표**: 설치, 재시작, 업그레이드, 복원 뒤에도 실제로 동작하는 기반

**범위**
- **D5** (`cd7ce96`): 아래 세 조건이 닫혀야 완료입니다.
  - 동시성 테스트가 잠금 경합을 강제로 만듭니다. `tests/schedule_worker_e2e.sql`이 `v_locked_by_a=false`도 통과시키던 경로를 없앱니다. (4.1절: `6c9453c`에서 처리, 리뷰어 검증 전)
  - 워커 호출 제거 변이의 실패 로그와 복원 후 통과 로그를 냅니다.
  - 문서의 "Exactly once"를 "같은 예약 발화에 대해 세션 중복 생성 없음"으로 좁힙니다.
- PG 재시작 후 웹과 워커가 자동으로 뜹니다. 놓친 실행 정책은 현재 기준(놓친 횟수와 관계없이 1회 실행, 그 뒤 `now()+interval`)을 문서화하고, cron 도입 때 다시 정의합니다.
- 업그레이드 스크립트를 만들고, 옛 버전 설치 → `ALTER EXTENSION UPDATE` → selftest 하네스를 **지금** 만듭니다. 이후 스키마 커밋마다 함께 갱신합니다. 버전 번호 확정만 RC 직전에 합니다.
- pg_dump/restore: seed 표시와 업그레이드 시 기존 seed 행 표시까지 포함합니다.
- 기존 관리자 보존을 검증합니다. Codex는 현재 bootstrap이 이미 임시 관리자만 지운다고 판단했으므로, 수정이 아니라 검증 조건으로 둡니다.
- 시크릿 평문 저장 해소: pgcrypto나 키가 없으면 명시적으로 실패합니다. 조용히 평문으로 되돌아가는 일은 금지합니다.
- pgcrypto가 없을 때 테스트가 조용히 건너뛰어지는 문제를 해소합니다(verify6 백로그 3·4번 포함).
- GHCR quickstart 이미지를 인증 없이 pull할 수 있게 합니다.
- quickstart 정확성: 실제 포트를 출력하고, Ollama/OpenAI 호환 예시와 allow-private-network의 필요성과 위험을 한 줄로 적습니다. 문서 전체 정비는 RC 직전에 합니다.
- verify6 백로그 C5~C9

**완료 정의**
1. 공개 이미지를 인증 없이 받아 문서대로 설치할 수 있습니다. 기존 관리자가 유지되고, 로그인과 Ollama 연결 안내가 맞습니다. pgcrypto나 키가 없으면 평문 저장이 일어나지 않습니다.
2. 실제 옛 버전에 사용자 설정, 권한, 암호화된 시크릿을 만든 뒤 업그레이드하고 selftest를 통과합니다. 그 뒤 실제 워커가 그 설정으로 fixture 호출을 완료합니다.
3. 별도 클러스터에 dump/restore한 뒤 로그인, 권한 허용과 거부, 시크릿을 쓰는 호출, 일정 발화가 모두 됩니다. 복원 후 테스트가 빠진 데이터를 다시 만들어 통과하는 일이 없어야 합니다.
4. D5에서 밀린 일정은 한 번 생성되고, 반복 종료 조건을 지키고, 강제 락 경합에서도 세션이 중복되지 않습니다. 생성된 세션은 실제 mock executor 응답까지 완료됩니다.
5. PG를 실제로 재시작해도 수동 조작 없이 웹과 워커가 복구되고, 정한 정책대로 예약을 처리합니다.
6. 변이: 워커 일정 호출 제거, 행 잠금 무력화, 자동 기동 누락, dump 대상 누락을 각 테스트가 잡아냅니다.

### 6.2 2단계: 최소 스키마 계약 문서 (리뷰 후 구현)

**목표**: 3단계에서 다시 만들 필요가 없도록 데이터의 의미와 관계를 먼저 고정합니다. 첫 출시에 필요한 것만 다룹니다.

**정할 계약**

| 계약 | 최소 내용 |
|---|---|
| 실행 주체 | (대신하는 사용자, 에이전트, 권한 출처)로 정의합니다. 소유자와 결과 수신자는 따로 둡니다. 요청자 신원은 인증 문맥에서 가져오고 모델 출력에서 받지 않습니다. 사용자가 비활성화되면 권한을 다시 검사합니다. |
| 일정 정의와 개별 실행 | 정의: 종류(cron 5필드/interval), IANA 시간대, 버전, 누락·중첩 정책, 승인 사본 연결. 실행: 예정 시각, 시도, 상태, 멱등 키. DST, 재시작, 지연 사례의 예정 시각과 멱등 키를 표로 확정합니다. |
| 공통 승인 계약 | 대상과 대상 버전, 요청자와 결정자, 채널(`chat_confirm` 또는 `queue`), 기한, 범위(능력·버전 상한, provider 지문, 최종 모델). 결정 기록에는 요청 사본, 규칙 버전, 이유를 남기고 **지금부터 저장**합니다. provider 지문에 들어갈 필드를 열거합니다. |
| 채팅 확인 | 만료 시각, 인증 사용자, 대화, 제안 ID, 정의 버전을 담은 PG 행으로 만듭니다. 확인은 그 행 ID에 결합하고 멱등입니다. 평문 "응"은 그 대화에 만료되지 않은 확인 요청이 정확히 하나이고 버전이 바뀌지 않았을 때만 받습니다. 그 외에는 다시 묻습니다. 결합은 SQL이 합니다. |
| 기억 | (scope_kind, scope_id) 구조로 두되 CHECK로 user와 agent만 허용합니다. 팀·조직은 **미지원**으로 명시하고, 나중에 CHECK만 넓히면 되게 합니다. 소유자, 출처, 만료와 정정도 정합니다. |
| 전달 대기열 | PG 안에 둡니다. 수신자, 원래 대화, 실행, 종류(승인 알림, 완료, 실패), 재시도, 읽음 여부, 중복 방지 키를 담습니다. |

| 기록 분리 | 운영 감사 기록과 Laya 학습용 표현을 분리합니다. v5의 P7과 '내보내기 무변환' 요구를 개정합니다(3.1절 P7, 7장). |
| 모델 출력 | 언제나 초안입니다. 서버가 정규화하고 사용자가 확인합니다. |

**완료 정의**
1. 각 계약에 필수 필드와 함께 신원 출처, 변경 가능 시점, 권한 철회, 실패, 삭제의 의미를 적습니다.

3. 변이 명세도 승인받습니다. 사용자 필터, 유일성 제약, 승인 버전 비교를 각각 제거했을 때 어떤 테스트가 실패해야 하는지 정합니다.
4. 최소 스키마 구현에는 제약, 인덱스, 업그레이드 경로가 붙습니다. 사용자 문맥이 채팅 매핑에만 기대지 않고 워커까지 전달되는 대표 경로를 확인합니다. 문서만 끝난 시점에는 실행 검증을 '미실행'으로 표시합니다.
5. 리뷰어가 검토를 마칩니다.

**병행 작업(지금, 1단계 진행 중): 프롬프트 스파이크.** 코드는 커밋하지 않습니다.
- 모델: Ollama 소형 모델 하나, OpenAI 호환 모델 하나
- 입력: "평일 9시 날씨", 시간대를 말하지 않은 요청, 수정 요청, 도구가 필요 없는 상기 요청
- 측정: JSON 파싱률과 의미 정확도를 따로 잽니다.
- 이 스파이크는 실행 검증을 대신하지 않습니다. 현재 액션 허용 목록에는 `propose_schedule`이 없습니다.

### 6.3 3a단계: 첫 사용 가능한 예약 에이전트 (브랜치 안에서 검증된 상태)

**목표**: "평일 오전 9시 서울 날씨 알려줘"를 한 문장으로 맡기는 데서 수정과 중지까지 이어지는 흐름. 여기까지가 Grok Bot 같은 최소 경험입니다.

**범위**
- `propose_schedule`
  - 액션 허용 목록에 추가하고, 입력 검증과 정규화를 합니다.
  - 제안을 저장합니다. 승인과 일정 생성은 같은 트랜잭션에서 처리합니다.
  - 요청자는 인증 문맥에서 가져옵니다.
- cron 5필드와 IANA 시간대를 지원하고, 다음 실행 시각을 보여 주고 확인받습니다.
- 웹 채팅의 확인 버튼과 평문 확인, 승인 알림
- 결과와 실패를 원래 사용자 채팅에 전달하고, 중복 전달을 막습니다.
- 중지와 수정
  - 중지: 일정을 비활성화하고 대기 중 실행을 취소합니다. 이미 나간 외부 호출은 취소를 보장하지 않습니다. 취소된 실행의 결과는 전달하지 않고 상태만 보여 줍니다.
  - 수정: 새 버전을 만들고 이전 버전의 대기 실행을 취소합니다.
- 사용자 범위 기억과 격리
- 최소 무인 정책
  - 중첩은 skip으로 고정합니다. 연속 3회 실패하면 정지하고 알립니다.
  - 실행별 호출 수와 벽시계 시간 한도는 가격 등록 여부와 관계없이 필수입니다. 한도가 없으면 등록을 거부합니다.
  - 비용은 기본이 unknown입니다. 관리자가 명시한 `is_free`만 0으로 봅니다. 사설망 주소는 무료의 근거가 아닙니다.
  - 예약 실행 문맥에서는 procedure 내부 `fn_llm_complete` 호출을 SQL로 거부합니다. 지금은 이 호출이 호출 수 한도에 잡히지 않기 때문입니다.
- 실행 가드
  - 매 호출마다 (에이전트 권한 ∩ 일정의 능력·버전 상한)으로 다시 검사합니다.
  - 최종 모델이 승인 사본과 다르면 실행 전에 거부합니다. 작업, 함수, procedure의 override도 포함합니다.
  - provider 지문이 바뀌면 일정을 정지하고 알립니다.
- mock일 때는 서버 상태에 근거해 "모의 실행—실제 추론·외부 작업 없음"을 표시합니다.
- 날씨는 기존 `seoul-weather`/`seoul_weather`(http_get 핸들러, 내부 LLM 없음)를 씁니다. 범용 HTTP 권한이나 새 커넥터는 이 단계의 선행 조건이 아닙니다.

**완료 정의**
1. 두 예시를 채팅에서 등록합니다.
   - (가) 평일 09시 서울 날씨: CI에서 `.invalid`나 로컬 fixture로 executor 도달과 오류의 채팅 전달을 확인합니다. 실제 서비스 성공은 수동 스모크로만 봅니다.
   - (나) 매일 08시 할 일 상기: 사용자 기억을 쓰고, 도구 호출이 없어야 합니다.
2. cron과 시간대의 다음 실행 시각이 맞습니다. 평일, 날짜 경계, DST 중복과 누락의 기대값을 고정하고, 재시작 뒤에도 의미가 같습니다.
3. 확인 처리: 버튼과 평문, 만료, 복수 확인, 정의 변경, 중복 RPC를 검증합니다. 다른 사용자나 다른 대화의 확인으로는 승인되지 않습니다. 승인 검사와 생성 사이에 변경이 끼어들 때의 원자성도 검증합니다.
4. 실제 워커 실행에서 능력 상한, 최종 모델, provider 지문, 호출 수와 시간 한도, 내부 LLM 거부, 중첩 skip, 연속 3회 실패 정지와 알림을 각각 확인합니다.
5. 경합 테스트 3종: 중지와 완료, 수정과 대기 실행, 전달 재시도 중복. 이전 버전과 취소된 결과는 전달되지 않습니다. 정상 결과와 실패는 원래 수신자에게 한 번만 보입니다. 두 사용자의 기억과 결과가 섞이지 않습니다.
6. 변이 8개: 사용자 격리, 확인 대상 결합, 능력 상한, 모델·지문 검사, 한도, 내부 LLM 거부, 취소 결과 억제, 전달 중복 방지를 하나씩 무력화하면 해당 테스트가 실패합니다. mock 체험과 실제 provider 체험의 결과는 따로 기록합니다.
7. 회귀 기준을 3a부터 계속 유지합니다. 능력이 바뀌거나 권한이 철회되어도 기존 일정의 상한을 우회할 수 없고, 철회는 다음 호출부터 바로 적용됩니다.

**완료 정의**

2. 실제 executor로 각 호출 유형을 발생시켜 호출 수와 비용 귀속을 검증합니다.

5. 변이: 예산 확보 생략, 내부·재시도·위임 집계 누락, 동시성 보호 제거 시 테스트가 실패합니다.

### 6.9 남은 이견

실질적 이견은 없습니다. Codex가 6라운드에서 "남은 실질적 반대 없음"을 밝혔습니다. 토론 중 PM이 처음 주장했다가 Codex 반론을 받아들여 바꾼 항목은 아래와 같습니다.
- 루프백/사설망 provider를 비용 0으로 보자는 안 → 관리자가 명시한 `is_free`만 0
- "가격 등록 **또는** 호출 한도" → 호출 수와 시간 한도는 항상 필수
- 스파이크 실패율이 높을 때만 서버 정규화를 넣자는 안 → 서버 정규화는 무조건
- 게이트 재검증을 `sql/`, `src/` 변경으로만 판정하는 안 → 영향 범위를 넓게 정의

### 6.10 v5 단계 상세 (참고)

#### v5 1단계: 사람 조직, 결재, 판단 지점, 판단 기록

**목표**: 판단 기록은 "누가 어떤 판단을 내렸나" 위에 쌓이므로, 사람 조직과 결재 모델을 먼저 만들고 그 위에 판단 지점과 판단 기록을 올립니다. 이 단계부터 판단 데이터가 쌓이기 시작합니다.

**1-1. 사람 조직**
- 사람(사용자)에게 소속(팀, 부서)과 역할(예: 마케팅 본부장, 법무 담당)을 붙입니다. 시스템 권한(`admin`/`user`)과 업무 역할은 분리합니다.
- 한 사람이 여러 역할을 가질 수 있습니다.

**1-2. 결재 모델**
- 승인 요청마다 **결정 권한자**를 규칙으로 정합니다. 예: "마케팅팀 작업의 외부 비용 발생 → 마케팅 본부장 역할", "물리 동작 → 설비 책임자 역할".
- 기한이 지나면 상위자에게 상정하고, 대리 결재자를 지정할 수 있습니다.
- 승인함은 "내가 결정해야 하는 것"을 기준으로 보여줍니다.
- 기존 `human_approvals`와 `change_proposals`는 이 모델 위로 옮깁니다. 기존 동작(관리자가 모두 결정)은 기본 규칙으로 남겨 호환성을 지킵니다.

**1-3. 판단 지점 등록**
- 판단 지점을 코드에 고정하지 않고 **데이터로 등록**합니다. 질문 형태, 선택지를 가져오는 곳, 결정 권한자, 위험 등급을 등록합니다(7장).
- Allgres가 기본 판단 지점을 제공하고, 조직이 새 판단 지점을 추가할 수 있습니다.

**1-4. 판단 기록**
- 판단 지점에서 결정이 나올 때마다 **Laya 공식 형식**으로 기록합니다(7.4절). Laya 사용 여부와 무관하게 항상 기록합니다.
- 학습용과 평가용 내보내기 기능(JSONL 파일 다운로드, 그리고 같은 내용을 반환하는 RPC)을 제공합니다.

**완료 기준**
- 마케팅 시나리오의 모든 승인이 정해진 권한자에게 가고 판단 기록이 쌓입니다.
- 내보낸 파일이 공식 `laya-evals validate`와 `laya-train --dry-run` 검사를 통과합니다(PG 밖에서 확인).

#### v5 2단계: 대시보드 정리 (UX 기반)

**목표**: 11장의 원칙에 따라 메뉴 구조와 첫 실행 경험을 다시 짭니다.

- 메뉴: **홈, 조직, 작업, 능력, 연결, 설정** 여섯 영역(11.2절).
- 첫 실행: 빈 화면에서 "모델 연결 → 팀 만들기 → 첫 일 맡기기" 안내. 모델 연결이 없으면 그 단계부터 이끕니다.
- 홈: 내가 결정할 것(승인함), 진행 중인 작업, 실패나 주의가 필요한 항목.
- 용어와 상태 표시 통일, 되돌리기 기본(11.3절).
- 판단 기록 화면: 판단 지점별 기록 수(사람, 규칙, LLM, Laya), 최근 판단, 내보내기.

**완료 기준**: 마케팅 팀 생성부터 첫 일 맡기기까지 메뉴를 헤매지 않고 한 흐름으로 끝납니다. 처음 쓰는 사람 기준으로 화면 점검을 통과합니다.

#### v5 3단계: 연결 (모델, MCP, API, 판단 모델)

**목표**: 외부와 연결하는 모든 것을 **연결** 영역 하나에서 같은 방식으로 다룹니다(9장).

| 종류 | 연결 방법 |
|---|---|
| 채팅 모델 | 제공사 선택 + 키. 연결 확인, 모델 목록 자동 조회, 가격 자동 입력(예산 상한이 바로 동작) |
| 임베딩 | 같은 방식(`purpose='embedding'`) |
| 판단 모델 | `purpose='decision'` 신규. 주소 + 키(선택) → `/health`로 상태 확인 → 사용 가능한 체크포인트와 버전 표시. Laya(`laya-serve`)와 Jev가 같은 요청 형식(`/v1/systemone`)이라 함께 지원 |
| MCP | 주소만 붙여넣기 → 인증 방식 자동 발견 → OAuth면 "로그인" 버튼 하나 → 도구 목록 표시 → **도구마다 위험 등급 확인** → 체크해서 능력으로 등록 |
| HTTP API | 기존 인증 방식(none, authorization, x-api-key) 유지 + 연결 테스트 |

추가 기능
- **로컬 MCP 서버**: stdio 방식 서버는 사용자가 PG 밖에서 HTTP 중계와 함께 띄우고, Allgres는 그 주소로 연결합니다. 연결 화면에 안내와 docker compose 예시를 제공합니다(9.5절).
- **들어오는 이벤트 받기**: 웹훅 수신 주소와 MCP 알림 구독. 받은 이벤트는 PG 큐에 쌓고 규칙에 따라 작업을 시작합니다(9.3절).
- **연결 관리**: 상태 표시, 도구 목록 변경 감지와 재승인, 토큰 갱신과 만료 알림, 연결이 끊기면 해당 능력을 쓰는 작업을 대기 처리(9.4절).

**완료 기준**: 리서치 MCP(OAuth 포함)를 주소 붙여넣기부터 에이전트 권한 부여까지 3분 안에 끝냅니다. 장비 제어 시나리오의 물리 동작 도구가 기본적으로 "승인 필요"로 등록됩니다.

#### v5 4단계: 능력(스킬) 생성: 크리에이터 에이전트와 사용법 문서

**목표**: 필요한 능력을 대화로 만들어 씁니다(10장).

- 크리에이터 에이전트가 요청을 듣고 **PG 안에서 되는지, MCP가 필요한지** 판단합니다.
  - PG 안: function(plpgsql)이나 procedure(사용법 문서) 초안을 만듭니다.
  - MCP 필요: 맞는 MCP 서버 연결을 제안하고, 연결 화면으로 안내합니다. 외부 서버 코드는 만들지 않습니다.
- 모든 생성물은 **초안 → 테스트 실행 결과 표시 → 사람 승인 → 등록** 순서를 거칩니다. 이 승인도 판단 지점이므로 기록이 쌓입니다.
- 크리에이터가 읽고 따르는 **사용법 문서**를 버전 관리되는 procedure로 작성합니다.

**완료 기준**: 마케팅 시나리오의 리서치 능력("웹 검색해서 출처까지 정리")을 대화만으로 만들어 리서치 에이전트에게 부여할 수 있습니다.

#### v5 5단계: 팀 협업 확장

**목표**: 4.2절의 조직 구조 한계를 풉니다.

- **여러 소속**: 에이전트가 여러 그룹에 속할 수 있게 합니다. 권한 상한과 비용 책임은 **주 소속** 기준으로 계산하고, 보조 소속은 업무 수신 경로만 엽니다.
- **팀 창구**: 팀 단위로 위임을 받는 창구를 둡니다. 다른 팀은 에이전트가 아니라 팀 창구에 맡기고, 팀 안에서 담당자를 정합니다.
  - 창구 담당 지정 방식: 지정된 접수 에이전트, 또는 사람이 배정. 사람 배정은 판단 지점이 되어 기록이 쌓입니다.
  - 권한 상한은 창구 기준으로 계산합니다. 맡기는 팀은 창구가 가진 상한 이상을 간접적으로 얻지 못합니다(D1과 같은 원칙).
- **공유 지식 범위**: 기억과 지식을 에이전트, 팀, 조직 세 범위로 나누고 읽기·쓰기 권한을 따로 둡니다.
- **협업 가시성**: 다른 팀에 맡긴 일의 진행 상황과 결과가 맡긴 쪽 화면에 보이고, 결과물에는 출처와 근거가 함께 넘어갑니다.

**완료 기준**: 12장의 매트릭스 조직 시나리오와 다팀 프로젝트 시나리오를 통과합니다.

#### v5 6단계: Laya 연결 (선택 기능)

**목표**: 판단 지점별로 사람 대신 Laya에게 위임할 수 있게 합니다(8장).

- 판단 지점마다 **끔 / 관찰 / 위임** 세 모드를 둡니다. 기본은 끔입니다.
- 요청은 공식 `laya-serve` API로 보내고, 판단 지점별 체크포인트(`model`)와 기준선(`min_confidence`)을 함께 보냅니다.
- 확신이 낮은 답(`low_confidence`), 오류, 시간 초과는 **결정 권한자인 사람에게 돌립니다.**
- 공식 단계적 도입 절차에 맞춰 화면에서 안내합니다. 관찰 → 일치율과 정확도 확인 → 범위를 제한한 위임 → 확대 → 문제 시 되돌리기.
- 학습과 평가는 Allgres 밖에서 공식 도구로 합니다. Allgres는 데이터를 내보내고, 평가 보고서를 받아 기록하고, 체크포인트 전환을 승인 절차로 관리합니다.

**완료 기준**: Laya를 연결하지 않은 상태에서 모든 시나리오가 정상 동작합니다. Laya를 연결한 상태에서는 선택한 판단 지점만 위임되고 나머지는 그대로입니다. Laya 서버를 중지해도 해당 판단이 사람에게 돌아가며 작업이 멈추지 않습니다.

## 7. 판단 지점과 판단 기록 상세

> **[v6: 5단계 설계 자료]** 결재선은 5단계 "조직과 결재선", Laya 형식 변환과 내보내기, 판단 기록 화면은 5단계 "Laya 변환과 내보내기"입니다. 상세 완료 정의는 5단계에 들어갈 때 다시 씁니다.
> **[v6 개정]** 운영 감사 기록과 Laya 학습용 표현을 분리합니다. 2단계 공통 승인 계약의 결정 기록(요청 사본, 규칙 버전, 이유)은 지금부터 저장합니다. 따라서 7.4절 기록 규칙 5("기록 시점에 이미 공식 형식이므로 내보낼 때 내용을 바꾸지 않는다")와 `decision_records`를 공식 JSONL 1줄의 본체로 두는 설계는 그대로 쓰지 않습니다. 분리 계약은 2단계(6.2절 "기록 분리")에서 정하고, Laya 표현으로의 변환과 내보내기는 5단계입니다. 아래 표는 v5 설계안 그대로 남깁니다.

### 7.1 판단 지점이란

판단 지점은 **"정해진 선택지 중 하나를 고르는 결정이 사람에게 요구되는 곳"** 입니다. 판단 지점은 다음을 갖습니다.

| 항목 | 내용 | 예 |
|---|---|---|
| 이름(질문 id) | 판단의 식별자. Laya 질문 id로 그대로 사용 | `approval_external_cost` |
| 질문 형태 | Laya 질문 형태: `choice`(선택), `score`(점수 단계), `noul`(예/아니오) | `choice` |
| 지시문 | 판단 기준 설명. Laya `instructions` | "이 외부 비용 지출을 승인할지 결정하라" |
| 선택지 출처 | 고정 목록, 또는 판단 시점에 조회(예: 팀 안의 에이전트 목록) | 고정: 승인 / 거절 / 수정 요청 |
| 선택지 설명 | 선택지마다 설명. Laya `criteria` | 승인: "예산 범위 안이고 목적이 명확함" |
| 상황 구성 방법 | 판단에 필요한 정보를 모아 `state`를 만드는 규칙 | 요청 내용, 금액, 남은 예산, 요청 에이전트, 근거 |
| 결정 권한자 | 결재 규칙에 따른 역할 | 마케팅 본부장 |
| 위험 등급 | 판단이 잘못됐을 때의 영향 | 중간 |
| 질문 버전 | 지시문이나 선택지 설명이 바뀌면 증가 | 3 |

### 7.2 기본 판단 지점 (권장, 14장 결정 필요)

**사람이 결정하는 곳**으로 시작하는 것을 권합니다. "사람 대신 Laya에게 위임"이라는 원칙(P6)에 정확히 맞고, 가장 귀한 데이터가 쌓이는 곳이기 때문입니다.

| 판단 지점 | 형태 | 선택지 | 지금 사람이 결정하는 순간 |
|---|---|---|---|
| 승인 요청 결정 | `choice` | 승인 / 거절 / 수정 요청 | 승인함에서 결정할 때 |
| 변경 제안 승인 (함수·사용법 문서 등록) | `choice` | 승인 / 거절 / 수정 요청 | 크리에이터 초안을 승인할 때 |
| 물리 동작 승인 | `choice` | 승인 / 거절 / 보류 | 장비 제어 도구 실행 전 |
| 팀 창구 담당 배정 | `choice` | 팀 안 담당자들 (판단 시점에 조회) | 사람이 담당자를 정할 때 |
| 결과 채택 | `choice` 또는 `score` | 채택 / 반려 / 수정 요청, 또는 품질 단계 | 사람이 결과를 검토할 때 |
| 요청 분류 수정 | `choice` | 조직이 정한 요청 유형 | 사람이 분류를 고칠 때 |

에이전트(LLM)가 스스로 내리는 결정(예: 위임하는 에이전트가 어느 팀에 맡길지 고르는 것)은 기본 판단 지점에 넣지 않습니다. 필요하면 조직이 판단 지점으로 등록할 수 있게 합니다(1-3).

### 7.3 판단 지점의 모드

| 모드 | 결정자 | Laya 호출 | 기록 |
|---|---|---|---|
| **끔** (기본) | 사람 | 안 함 | 사람의 결정 |
| **관찰** | 사람 | 함. 결과는 기록만 하고 결정에 쓰지 않음 | 사람의 결정 + Laya 결과 |
| **위임** | Laya. 확신이 낮거나 오류면 사람 | 함 | Laya 결정 또는 사람의 결정 + Laya 결과 |

위임 모드에서도 **적용 범위를 제한**할 수 있습니다(공식 도입 가이드의 "bounded slice"). 예: 금액 50만 원 이하만, 되돌릴 수 있는 동작만, 특정 팀만, 하루 N건까지. 범위 밖이면 사람에게 갑니다.

### 7.4 판단 기록 구조

**기록 규칙**
1. **판단 당시의 질문과 선택지를 사본으로 고정합니다.** 나중에 팀이나 에이전트 구성이 바뀌어도 당시 기록은 그대로 학습에 쓸 수 있습니다.
2. **Laya에 보낼 입력과 기록에 남길 입력을 같은 함수로 만듭니다.** 학습 때 본 형태와 실제 질문 형태가 어긋나는 것을 막습니다.
3. **기록은 수정하거나 지우지 않고 추가만 합니다.** 사람이 나중에 고치면 원래 기록에 연결된 정답을 추가합니다.
4. **Laya 사용 여부와 무관하게 항상 기록합니다.**
5. **PG는 담아두고 넘겨주기만 합니다.** 기록 시점에 이미 공식 형식이므로, 내보낼 때 내용을 바꾸지 않습니다. **[v6에서 개정됨: 기록 분리, 이 장 머리말 참고]**

**테이블 (설계안)**

`decision_points`: 판단 지점 정의
| 열 | 내용 |
|---|---|
| `point_id` | 기본키 |
| `question_id` | Laya 질문 id |
| `qtype` | `choice` / `score` / `noul` |
| `version` | 질문 버전 |
| `instructions`, `criteria_source`, `state_builder` | 7.1절 항목 |
| `decider_rule` | 결정 권한자 규칙 |
| `risk_level` | 위험 등급 |
| `mode` | 끔 / 관찰 / 위임 |
| `laya_model`, `laya_min_confidence`, `delegation_scope` | Laya 설정(v5 6단계, v6 5단계) |

`decision_records`: 판단 1건 = 공식 JSONL 1줄의 본체
| 열 | 내용 |
|---|---|
| `record_id` | 기본키 |
| `point_id`, `point_version` | 어느 판단 지점의 어느 버전 |
| `state` | Laya `state` 그대로 (jsonb 또는 text) |
| `questions` | Laya `questions` 그대로. 판단 시점의 사본: `{"<question_id>": {"type": ..., "instructions": ..., "criteria": {...}}}` |
| `decided_by` | `human` / `rule` / `laya` |
| `decider` | 결정한 사람, 또는 체크포인트 이름 |
| `answer` | 실제로 적용된 답 |
| `laya` | Laya를 호출한 경우만: `run_id`, 체크포인트와 버전, 선택지별 확률, `answer_confidence`, 기준선, 넘김 여부, 응답 시간, 오류 |
| `split` | `train` / `eval`. 기록 id 해시로 정하며 한 번 정하면 바뀌지 않음 |
| `context` | 작업 id, 팀, 언어, 개인정보 처리 상태, 시각 |

`decision_labels`: 기록에 붙는 정답
| 열 | 내용 |
|---|---|
| `record_id` | 대상 기록 |
| `expected` | Laya `expected` 그대로: `{"<question_id>": <답>}` |
| `tier` | `gold`(사람 결정 또는 사람 확인) / `silver`(실제 결과로 확인) / `bronze`(LLM 판정) |
| `source`, `labeled_by`, `labeled_at`, `note` | 근거 |

**정답이 붙는 경우**
- 사람이 판단 지점에서 직접 결정하면 그 결정이 곧 `gold` 정답입니다.
- Laya가 위임 모드에서 결정한 건은 정답이 아닙니다. 사람이 나중에 확인하거나 고치면 `gold`, 실제 결과(예: 반려된 결과물, 되돌린 동작)로 확인되면 `silver`가 붙습니다.
- LLM 검증 결과는 `bronze`이며, 기본적으로 학습 내보내기에서 제외합니다.
- **Laya 자신의 결정은 정답으로 쓰지 않습니다.**

### 7.5 내보내기

**학습용** (공식 `laya-train` JSONL, 한 줄에 한 기록)
```json
{"state": "요청: 웨비나 광고 집행\n금액: 1,200,000원\n남은 예산: 5,000,000원\n요청 에이전트: marketing_strategist\n근거: 1분기 체험 가입 300건 목표",
 "questions": {"approval_external_cost": {"type": "choice",
   "instructions": "이 외부 비용 지출을 승인할지 결정하라",
   "criteria": {"approve": "예산 범위 안이고 목적이 명확함",
                "reject": "예산 초과이거나 목적이 불명확함",
                "revise": "목적은 타당하나 금액이나 범위 조정 필요"}}},
 "expected": {"approval_external_cost": "approve"}}
```

**평가용** (공식 `laya-evals` JSONL): 같은 형식이며, `split='eval'`인 기록만 내보냅니다.

**내보내기 규칙**
- 기록에 정답이 여러 개면 `gold` > `silver` > `bronze` 순서로 하나만 씁니다.
- 기본은 `gold`와 `silver`만 내보냅니다. `bronze` 포함 여부는 옵션입니다.
- 판단 지점, 질문 버전, 기간, 팀, 언어로 걸러 낼 수 있습니다.
- 개인정보는 판단 지점에 정해진 가림 규칙을 내보내기 직전에 적용합니다. 원본은 PG에만 남습니다. **[v6: 원본 보관과 삭제는 2단계 개인정보 삭제 최소 계약을 따릅니다. 감사 보존 정책 전체는 5단계입니다.]**
- 내보낼 때마다 내보내기 기록을 남깁니다: 조건, 건수, 파일 해시, 요청자.
- 학습용과 평가용은 `split`으로 나뉘므로 겹치지 않습니다. 공식 `laya-evals`도 겹침을 검사합니다.

## 8. Laya 연동 상세 (공식 표준만 사용)

> **[v6: 5단계 "Laya 변환과 내보내기"의 설계 자료]** 공식 표준만 사용한다는 원칙(P8)은 그대로입니다.

### 8.1 Laya란 (확인된 사실)

- Convai Innovations의 오픈소스(Apache-2.0) 판단 모델입니다. 저장소는 [NandhaKishorM/laya](https://github.com/NandhaKishorM/laya)이고 PyPI 패키지 이름은 `laya`입니다.
- 상황(`state`)과 정해진 형태의 질문(`choice`, `score`, `noul`)을 주면, **한 번의 계산으로** 답과 보정된 확률, 확신도를 돌려줍니다. 문장을 생성하지 않으므로 답을 파싱할 일이 없습니다.
- 체크포인트
  | 이름 | 기반 | 특징 |
  |---|---|---|
  | english | ModernBERT-large 421M | 영어 최적화 |
  | multilingual | mmBERT-base 322M | 100개 이상 언어. 보정값이 없는 채로 배포됨 |
  | typed-decisions | ModernBERT-large 421M | 공식 벤치마크 업무 4종에 파인튜닝 |
- **파인튜닝이 전제입니다.** 공식 벤치마크에서 기본 체크포인트(0.362)는 "가장 흔한 답만 고르기"(0.461)보다 낮고, 같은 데이터로 파인튜닝하면 0.77 수준입니다. 공식 문서도 능력은 파인튜닝에서 나온다고 설명합니다.
- 배포된 체크포인트는 확신을 과하게 표시합니다. 보정은 공식 학습 과정에 포함돼 있습니다.
- 속도(공식 벤치마크)
  | 환경 | 질문 1개 | 질문 10개 |
  |---|---|---|
  | GPU (T4) | 약 33ms | 약 72ms |
  | 노트북 CPU (최적 스레드) | 약 290~330ms | 약 2.6초 |
- Jev(TypeSafe)는 같은 요청 형식을 쓰는 호스팅 판단 API입니다. `laya-serve`는 Jev 요청 형식(`/v1/systemone`)과 호환됩니다.

### 8.2 Allgres와 Laya의 역할 경계 (공식 가이드 기준)

공식 [단계적 도입 가이드](https://github.com/NandhaKishorM/laya/blob/main/docs/staged-adoption.md)의 경계를 그대로 따릅니다.

| Laya가 제공 | Allgres(애플리케이션)가 소유 |
|---|---|
| 답, 선택지별 확률, 확신도, `run_id`, 체크포인트 정보 | 기존 결정자(사람), 실제 실행, 적용 범위 규칙, 기준선 정책, 검토, 대체 처리, 되돌리기, 기록 |

### 8.3 사용하는 공식 구성 요소

| 용도 | 공식 구성 요소 | Allgres가 하는 일 |
|---|---|---|
| 추론 | `laya-serve` (공식 Docker 이미지, CUDA·ARM 이미지와 compose 제공) | 판단 프로바이더로 HTTP 호출: `POST /v1/systemone`, `/v1/systemone/batch`, `GET /health` |
| 체크포인트 지정 | 요청의 `model` 필드 | 판단 지점별로 사용할 체크포인트 이름을 저장해 요청에 실음 |
| 넘기기 기준선 | 요청의 `min_confidence` (숫자 하나, 또는 `choice:2`, `choice:3-5` 같은 구간별 맵 + `default`) | 판단 지점별로 정책 값을 저장해 요청에 실음. 응답이 `low_confidence`면 사람에게 넘김 |
| 버전 확인 | `/health`의 `loaded`, `revisions` | 판단 기록에 실제 답한 체크포인트와 버전을 남김 |
| 인증 | `LAYA_API_KEY` (Bearer) | 판단 프로바이더 연결 정보에 키를 암호화해 저장 |
| 새 체크포인트 등록 | `LAYA_CHECKPOINT_PATH`, `LAYA_EXTRA_MODELS` (서버 시작 시) | 관여하지 않음. 운영자가 공식 방식으로 등록하고 서버를 재시작 |
| 학습 | `laya-train` CLI 또는 공식 노트북(Kaggle 2×T4, Apple Silicon) | 공식 형식 학습 데이터를 내보냄 |
| 평가 | `laya-evals run` (정확도·ECE 기준, 기준 버전 대비 비교, 실패 시 종료 코드 1) | 공식 형식 평가 데이터를 내보내고, 평가 보고서(JSON)를 받아 기록 |
| 도입 절차 | 공식 단계적 도입 가이드 | 끔/관찰/위임 모드와 적용 범위 제한으로 구현 |

### 8.4 운영 흐름

**처음 연결할 때**
1. 운영자가 공식 이미지로 `laya-serve`를 띄웁니다(PG 밖).
2. Allgres 연결 화면에서 판단 모델을 추가합니다. 주소와 키를 넣으면 `/health`로 상태를 확인합니다.
3. 판단 엔진 화면에서 판단 지점을 하나 골라 **관찰** 모드로 켭니다. 체크포인트와 기준선을 지정합니다.
4. 관찰 기간 동안 사람의 결정과 Laya 결과의 일치율, 정답 대비 정확도, 넘김 비율을 화면에서 확인합니다.

**학습할 때**
1. 판단 엔진 화면이 "이 판단 지점은 사람 판단이 N건 쌓여 학습 가능" 같은 안내를 표시합니다. N의 기본값은 공식 문서의 학습량 기준을 참고해 정합니다.
2. 운영자가 학습용, 평가용 데이터를 내보냅니다.
3. PG 밖에서 공식 도구로 학습하고 평가합니다.
   ```bash
   laya-train --data train.jsonl --base english --out ./ckpt-2026-11 --target-error 0.10
   laya-evals run eval.jsonl --model ./ckpt-2026-11 --min-accuracy 0.8 --max-ece 0.05 --json report.json
   ```
   화면은 이런 공식 명령을 판단 지점에 맞춰 채워서 보여줍니다.
4. 운영자가 공식 방식으로 새 체크포인트를 `laya-serve`에 등록하고 재시작합니다.
5. Allgres에 평가 보고서를 올리고, 해당 판단 지점의 체크포인트 전환을 요청합니다. 이 요청은 승인 절차를 거칩니다.
6. 새 체크포인트는 먼저 관찰 모드로 비교한 뒤, 위임 범위를 단계적으로 넓힙니다.

**되돌릴 때**
- 이전 체크포인트가 서버에 계속 등록돼 있으면, 판단 지점의 `model`을 이전 이름으로 바꾸는 것만으로 즉시 되돌립니다.
- 위임 모드를 끄면 바로 사람에게 돌아갑니다.

**장애 시**
- Laya 서버가 응답하지 않거나, 시간이 초과되거나, 오류를 내면 해당 판단은 결정 권한자에게 갑니다. 작업은 멈추지 않습니다.
- `laya-serve`가 재시작하는 동안에도 같습니다.

### 8.5 하지 않는 것

- PG 안에서 Laya 실행(공식 Rust 포트 `laya-onnx`도 쓰지 않음, P3)
- Laya 학습·평가를 위한 자체 컨테이너, 래퍼, MCP 서버 제작(P8)
- PG에서 기준선이나 온도를 재계산하는 자체 보정(공식 학습 과정의 `--target-error`와 보정 결과를 사용)
- 비슷한 사례를 찾아 Laya 입력에 덧붙이는 자체 사례 기억(공식 기능이 아님)

**참고**: 공식 표준에는 실시간(온라인) 학습이 없습니다. 실시간으로 일어나는 것은 **판단 기록이 즉시 쌓이는 것**까지이고, 모델이 좋아지는 것은 재학습과 체크포인트 전환을 통해서입니다.

## 9. MCP 확장 모델 상세

> **[v6: 5단계 "커넥터와 능력"의 설계 자료]** 범용 HTTP 권한과 새 커넥터는 5단계로 미뤘습니다. 3a의 날씨 예시는 기존 `seoul-weather`/`seoul_weather`를 씁니다. 이벤트 수신(9.3절)은 v6에 단계 배정이 없습니다(14장 O7).

### 9.1 연결 흐름 (사용자 기준)

1. 연결 → MCP → 주소 붙여넣기.
2. Allgres가 서버에 접속해 인증 요구를 확인합니다.
   - 인증이 필요 없으면 바로 3번으로 갑니다.
   - OAuth면 보호 리소스 메타데이터(Protected Resource Metadata)로 인증 서버를 찾습니다. 클라이언트 등록은 최신 MCP 인증 사양에서 우선 권장하는 Client ID Metadata Document 방식을 쓰고, 필요하면 동적 등록(DCR)으로 대체합니다. 그다음 PKCE로 로그인합니다. 사용자는 "로그인" 버튼과 제공사 로그인 화면만 봅니다.
   - API 키 방식이면 키 입력칸을 보여줍니다.
3. 도구 목록을 보여줍니다. 도구마다 이름, 설명, 입력 형식, **제안된 위험 등급**을 표시합니다.
4. 사용자가 쓸 도구를 체크하고 위험 등급을 확인하면 능력으로 등록됩니다.
5. "이 도구를 쓸 에이전트"를 바로 고를 수 있습니다. 권한 상한 규칙이 적용됩니다.

### 9.2 도구 단위 위험 등급

| 등급 | 예 | 기본 실행 규칙 |
|---|---|---|
| 조회 | 웹 검색, 전력 사용량 조회, 장비 상태 조회 | 허용 |
| 변경 | 사내 시스템에 글 등록, 일정 생성, 메일 발송 | 승인 필요(조직이 허용으로 바꿀 수 있음) |
| 물리 동작 | 밸브 열기, 장비 정지, 설정값 변경 | **승인 필요. 기본값으로 고정하고 바꾸려면 관리자 확인이 필요** |

- 등급은 도구의 메타데이터(예: MCP 도구 주석)를 참고해 **제안만** 하고, 최종 등급은 연결하는 사람이 확인합니다.
- 실행 규칙(`execution_rules`의 허용/승인/거부)과 권한 상한은 도구 단위로 적용됩니다.
- 변경·물리 동작의 승인은 판단 지점이므로 기록이 쌓이고, 원하는 범위만 Laya에 위임할 수 있습니다. 물리 동작 위임은 적용 범위 제한을 필수로 합니다.

### 9.3 들어오는 이벤트

- **주기 조회**: 기존 일정 기능으로 조회 도구를 주기적으로 호출합니다. 지금 바로 가능합니다.
- **웹훅 수신**: 연결마다 수신 주소와 서명 검증 키를 발급합니다. 받은 이벤트는 PG 큐에 쌓고, 이벤트 규칙(예: "전력 사용량 이상 → 설비팀 창구에 작업 생성")에 따라 작업을 시작합니다.
- **MCP 알림 구독**: 서버가 지원하면 리소스 변경 알림을 구독합니다. 받은 알림은 웹훅과 같은 큐로 들어갑니다.
- 이벤트 폭주에 대비해 연결별 수신 한도와 중복 제거를 둡니다.

### 9.4 연결 관리

- 상태 표시: 정상, 인증 만료 임박, 인증 만료, 응답 없음.
- 토큰 자동 갱신과 만료 알림.
- **도구 목록 변경 감지**: 도구가 추가되면 알림만 보냅니다. 기존 도구의 설명이나 입력 형식이 바뀌면 해당 도구를 일시 중지하고 재승인을 요청합니다. 도구가 사라지면 해당 능력을 비활성화합니다.
- 연결이 끊기면 그 능력을 쓰는 작업은 실패 대신 대기 상태로 두고, 복구되면 이어서 진행합니다.

### 9.5 로컬 MCP 서버

- `npx`, `uvx`, `python` 등으로 실행하는 stdio 방식 MCP 서버도 **PG 밖에서** 띄웁니다.
- stdio를 HTTP로 바꿔 주는 공개 중계 도구와 함께 컨테이너로 띄우고, Allgres는 그 HTTP 주소로 연결합니다. 연결 이후에는 원격 MCP와 똑같이 다룹니다.
- Allgres는 연결 화면에 안내와 docker compose 예시만 제공합니다. 중계 도구를 직접 만들거나 내장하지 않습니다.

### 9.6 실시간 제어의 경계

| Allgres (PG + 에이전트) | MCP 서버 (장비 쪽) |
|---|---|
| 목표 설정, 계획, 승인, 이상 대응 판단, 기록 | 밀리초~초 단위 제어 루프, 안전 정지, 장비 고유 인터록 |

- 실시간 제어 루프는 LLM이나 PG를 거치지 않습니다.
- 이 경계를 크리에이터 에이전트의 사용법 문서에 명시해, 크리에이터가 제어 루프를 Allgres 쪽 함수로 만들려 하지 않게 합니다.

## 10. 능력(스킬) 생성: 크리에이터 에이전트

> **[v6: 단계 배정 없음]** v6 합의안에는 크리에이터 에이전트 항목이 따로 없습니다(14장 O7).

### 10.1 능력의 종류

| 종류 | 어디서 동작 | 만드는 방법 |
|---|---|---|
| PG 함수 (`plpgsql`) | PG 안 | 크리에이터가 초안 작성 → 승인 |
| 단순 HTTP 함수 (`http_get` 등) | Rust 워커가 호출 | 크리에이터가 초안 작성 → 승인 |
| 사용법 문서 (procedure) | 에이전트 프롬프트 안내 | 크리에이터가 초안 작성 → 승인. 버전 관리 |
| MCP 도구 (`mcp_call`) | 외부 MCP 서버 | 연결 화면에서 도구를 등록. 크리에이터는 연결을 제안만 함 |

### 10.2 크리에이터의 판단 순서

1. **이미 있는 능력으로 되는가?** 능력 검색으로 확인합니다. 있으면 권한 부여만 제안합니다.
2. **PG 안에서 되는가?** 데이터 조회와 가공, 규칙 계산, 정해진 주소로의 단순 HTTP 호출이면 PG 함수나 HTTP 함수를 만듭니다.
3. **절차나 요령의 문제인가?** "이런 순서로 조사하고 이렇게 정리하라"면 사용법 문서를 만듭니다. 이미 있는 능력들을 엮는 경우도 여기에 해당합니다.
4. **외부 세계와 닿아야 하는가?** 웹 탐색, 장비, 사내 시스템이면 맞는 MCP 서버를 제안하고 연결 화면으로 안내합니다. 연결된 뒤 사용법 문서로 쓰는 법을 묶습니다.

### 10.3 생성 절차

1. 사용자 요청 → 크리에이터가 위 순서로 판단하고, 무엇을 만들지 한 문단으로 설명합니다.
2. 초안 작성: 이름, 설명, 입력 형식, 본문, 필요한 권한, 위험 등급.
3. 테스트 실행: 안전한 범위에서 시험 실행한 결과를 보여줍니다. 변경이나 물리 동작은 시험 실행을 생략하고 그 사실을 표시합니다.
4. 사람 승인: 변경 제안으로 올라가고, 결정 권한자가 승인합니다(판단 지점, 기록이 쌓임).
5. 등록 후 "이 능력을 쓸 에이전트"를 고르게 합니다.

### 10.4 크리에이터가 읽는 사용법 문서 (작성 대상)

- 능력 종류별 작성법과 예제(plpgsql 함수, HTTP 함수, 사용법 문서)
- PG 안에서 할 일과 MCP로 할 일의 구분 기준(10.2절, 9.6절)
- 권한 원칙: 최소 권한, 권한 상한, 시스템 에이전트 금지
- 위험 등급 판정 기준(9.2절)
- 테스트 방법과 금지 사항(비밀값 하드코딩 금지, 외부 호출 대상 제한 등)
- 판단 지점 등록 방법(7.1절). 새 결정이 반복적으로 사람에게 요구되면 판단 지점으로 등록하도록 제안

## 11. UX/UI 원칙과 화면 구조

### 11.1 원칙

1. **한 화면에 한 가지 주요 행동.** 화면마다 가장 중요한 버튼 하나가 분명해야 합니다.
2. **점진적 공개.** 처음에는 꼭 필요한 입력만 보여주고, 고급 설정은 접어 둡니다.
3. **좋은 기본값.** 대부분의 사용자가 기본값 그대로 끝낼 수 있어야 합니다(위험 등급, 실행 규칙, 판단 지점 모드).
4. **자동으로 알아낼 수 있는 건 묻지 않는다.** 모델 목록, 가격, MCP 인증 방식, 도구 목록.
5. **빈 화면은 안내다.** 비어 있는 화면은 다음에 할 일을 보여줍니다.
6. **확인창보다 되돌리기.** 되돌릴 수 있는 작업은 바로 실행하고 되돌리기를 제공합니다. 되돌릴 수 없는 작업만 확인창을 띄웁니다.
7. **즉시 피드백.** 연결 테스트, 저장, 실행 결과를 그 자리에서 보여줍니다.
8. **쉬운 말, 하나의 용어.** 내부 용어(resource_type, handler) 대신 사용자 용어를 쓰고, 한 개념에는 한 단어만 씁니다.
9. **거부에는 이유를.** 권한 상한이나 규칙 때문에 막힐 때 왜 막혔고 어떻게 하면 되는지 보여줍니다.
10. **상태 표시 일관성.** 실행 중, 대기, 승인 대기, 실패, 완료를 모든 화면에서 같은 색과 문구로 표시합니다.

### 11.2 메뉴 구조

> **[v6]** v6의 화면 작업은 3a의 mock 표시, 3b의 기본/고급 설정 분리(최소 범위: 기본에는 이름, 모델, 프롬프트만)와 체험 모드 전환·안내 UI입니다. 아래 전체 메뉴 개편은 v6 합의안에 단계 배정이 없습니다(14장 O7).

| 영역 | 내용 |
|---|---|
| **홈** | 내가 결정할 것(승인함), 진행 중인 작업, 주의가 필요한 항목, 첫 실행 안내 |
| **조직** | 캔버스(팀, 에이전트, 위임 경로), 사람과 역할, 결재 규칙 |
| **작업** | 작업 목록, 대화, 실행 기록 다시 보기, 판단 기록 |
| **능력** | 함수, 사용법 문서, MCP 도구, 크리에이터와 대화 |
| **연결** | 채팅 모델, 임베딩, 판단 모델, MCP 서버, HTTP API, 이벤트 수신, 판단 엔진(판단 지점별 모드) |
| **설정** | 계정, 보안, 감사 기록, 백업 |

### 11.3 용어 (화면 표기 통일안)

| 화면 용어 | 뜻 | 대체할 기존 표현 |
|---|---|---|
| 능력 | 에이전트가 쓸 수 있는 함수, 사용법 문서, MCP 도구의 총칭 | 스킬, 함수, 도구, abilities |
| 위임 | 다른 에이전트나 팀 창구에 일을 맡길 수 있는 관계 | delegation, agent 권한 |
| 권한 상한 | 위임을 통해서도 넘을 수 없는 권한의 한계 | ceiling |
| 승인 | 사람이 결정해야 하는 요청 | approval, change proposal |
| 판단 지점 | 결정이 기록되고 Laya에 위임할 수 있는 곳 | 없음(신규) |

## 12. 검증 시나리오

> **[v6]** v6의 첫 사용 시나리오는 3a의 두 예시입니다: (가) 평일 09시 서울 날씨, (나) 매일 08시 할 일 상기(6.3절 완료 정의 1). 아래 S1~S5는 조직, 결재, Laya를 다루므로 5단계 설계 자료로 남깁니다. S1의 "단계별 확인"과 S5의 "6단계 이후"는 v5 단계 번호입니다(18장 대응표). S1의 0단계 항목(D1~D3)은 해결되었습니다(4.1절). 부하 테스트는 v6에 단계 배정이 없습니다(14장 O7).

각 시나리오는 **논리 시뮬레이션(글로 단계별 진행) → 막히는 곳 목록 → 구현 → 실제 화면 재현** 순서로 씁니다. 시뮬레이션 단계에서는 구현하지 않습니다(P9).

### S1. 마케팅 부서: 리서치 → 분석 → 방향 결정 (기준 시나리오)

**구성**
- 마케팅본부: 마케팅 본부장(에이전트), 시장 조사(market_researcher), 경쟁사 분석(competitor_analyst), 마케팅 전략가(marketing_strategist)
- 영업본부: 매출 데이터(sales_insights, `v_sales` 뷰 조회)
- 사람: 마케팅 본부장(사람, 외부 비용 승인 권한자)

**흐름**
1. 사용자가 마케팅 본부장 에이전트에게 "1분기 마케팅 방향을 정해줘"라고 요청합니다.
2. 본부장 에이전트가 시장 조사, 경쟁사 분석, 영업본부 창구(매출 분석)에 일을 나눠 맡깁니다.
3. 시장 조사와 경쟁사 분석은 리서치 MCP의 `web_search`로 조사하고 출처를 남깁니다. 시장 조사는 핵심 수치를 기억에 저장합니다.
4. 영업본부의 매출 에이전트가 지역별 매출을 조회합니다.
5. 본부장 에이전트가 결과를 모아 전략가에게 넘기고, 전략가가 타깃, 메시지, 채널, KPI를 제안합니다.
6. 광고 집행처럼 외부 비용이 드는 실행안은 사람 본부장의 승인으로 갑니다(판단 지점 기록).
7. 결과물을 사람이 채택하거나 반려합니다(판단 지점 기록).

**확인 항목**
- 0단계: 리서치 함수를 권한 선택지에서 고를 수 있는가(D3). 상한 우회와 시스템 에이전트 위임이 막히는가(D1, D2).
- 1단계: 승인이 사람 본부장에게 가는가. 판단 기록이 공식 형식으로 쌓이는가.
- 2~4단계: 처음 쓰는 사람이 연결, 능력 생성, 팀 구성, 일 맡기기를 안내만 보고 끝낼 수 있는가.
- 5단계: 영업본부 창구로 맡겨지는가.

### S2. 매트릭스 조직: 공용 법무 검토

- 법무 검토 에이전트가 법무팀(주 소속)과 마케팅, 영업(보조 소속)에 함께 속합니다.
- 마케팅과 영업이 각자 광고 문구와 계약 초안의 검토를 맡깁니다.
- 확인: 여러 소속, 권한 상한(주 소속 기준), 비용 책임, 공유 지식(법무 가이드)의 읽기 권한.

### S3. 다팀 프로젝트: 신제품 출시

- 마케팅, 영업, 개발, 디자인에서 구성원을 빌려온 프로젝트 그룹을 만듭니다.
- 프로젝트 공유 지식(출시 일정, 메시지 가이드)을 함께 갱신합니다.
- 확인: 프로젝트 그룹, 팀 창구 간 위임, 진행 상황 가시성, 공유 지식 쓰기 권한.

### S4. 긴 결재선: 예산 집행

- 요청 → 팀장 승인 → 본부장 승인 → 재무 확인의 3단 결재. 기한이 지나면 상위자에게 상정하고, 휴가 중이면 대리 결재합니다.
- 확인: 결재 규칙, 상정, 대리, 판단 기록(단계별), 승인함의 "내가 결정할 것".

### S5. 운영과 장비 제어: 전력 이상 대응

- 전력모니터링 MCP(조회, 이상 알림)와 설비제어 MCP(상태 조회, 부하 차단)를 연결합니다.
- 전력 이상 이벤트 수신 → 설비팀 창구에 작업 생성 → 에이전트가 원인 조사(조회 도구) → 부하 차단 제안 → 설비 책임자 승인(물리 동작) → 실행 → 결과 기록.
- 확인: 이벤트 수신, 도구 위험 등급, 물리 동작 기본 승인, 연결 끊김 시 대기, 실시간 제어 경계(9.6절).
- 6단계 이후: "부하 차단 승인"을 관찰 모드로 켜고 일치율을 확인합니다. 위임은 적용 범위 제한(특정 설비, 특정 시간대, 하루 N회)과 함께만 허용합니다.

### 부하 테스트

- 에이전트 수(10, 100, 500), 동시 작업 수(10, 100, 1,000), 판단 기록 누적량(10만, 100만 건)에서 응답 시간, 처리량, 저장 공간을 측정합니다.
- 결과를 기준으로 규모 한계를 `KNOWN_ISSUES.md`에 명시합니다.

## 15. 범위 밖

- PG 안에서 모델 실행(LLM, 임베딩, 판단 모델 모두)

- 브라우저 화면을 Rust(WASM)로 다시 작성하는 것

| 위험 등급 | 도구나 판단이 잘못됐을 때의 영향 등급(조회 / 변경 / 물리 동작) |
